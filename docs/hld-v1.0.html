01 / DECISION

Discover three. Deliver one. Prove reuse on the second.

Start discovery for Trees A, B, and C together. Build Tree A through the entire workflow before implementing the other two. This exposes shared evidence needs early while giving the team one concrete integration target.

The central boundary: trees consume a versioned patient snapshot. They never call P, C, or an LLM. The same tree, snapshot, policy version, and evaluation time must produce the same next node.

Hub-and-spoke is an established orchestration pattern, not a universal industry standard. It fits this workload when the hub is a deterministic application controller and the spokes are narrowly scoped evidence capabilities. Google describes both coordinator-based systems and tradeoffs between single- and multi-agent designs. [1]

Adopt now

One Python executor, versioned YAML trees, a stable snapshot contract, durable human review, and per-node audit events.

Keep small

Three logical runtime agent roles, implemented through one shared ADK runner and reusable skills. Agents do not need separate deployments.

Defer

Autonomous prescribing, clinical writeback, dynamic agent swarms, cross-tree recommendation synthesis, and a general visual tree editor.

Adding Tree B is primarily a YAML change only when its evidence concepts, predicates, and review policies already exist. New clinical concepts may require an adapter, normalization rule, or skill plus validation.

02 / SYSTEM BOUNDARY

A deterministic hub with evidence spokes

  1. The API binds the request to an authorized patient/encounter and an explicit approved tree version.
  2. The controller reads the current node’s evidence requirements and schedules only missing or expired evidence work. Independent reads may execute concurrently.
  3. Adapters retrieve structured data; agents handle unstructured extraction and ambiguous terminology. A deterministic validator accepts evidence or records a blocking status.
  4. The executor evaluates one node at a time against a pinned snapshot and recorded evaluation time. Gates stop progression until requirements are satisfied.
  5. The UI presents the evidence, path, and review task. Approved terminal output becomes a reviewed recommendation, with no automatic clinical writeback.

Different runs can execute concurrently. A single run has one active clinical traversal writer. Supporting N trees means sharing the pipeline across trees; it does not authorize combining their recommendations automatically.

Data sources are tools; skills describe how to use them

Expose P, C, and document retrieval through typed, read-only tools such as fetch_lab_results(patient_ref, encounter_ref) and fetch_culture_results(patient_ref, encounter_ref). Each tool wraps a source adapter, enforces authorization, and returns records with provenance. The controller binds the patient scope; the model cannot widen it.

A skill is the reusable procedure for an evidence task: which permitted tools to use, what fields to extract, how to express candidates, and when to abstain. A source itself is not a skill. Structured tool results may go directly to the validator; ADK is invoked when interpretation is needed. Skills guide interpretation, while Python validators enforce acceptance.

Skills are reusable, versioned contracts

Define a skill as instructions plus a typed input/output contract, allowed tools, deterministic validators, examples, and evaluation cases. This is an application contract, independent of any framework’s packaging conventions. The hub selects skills through an approved registry mapping evidence concepts to capabilities.

skills/
  extract_lab_observation/v1/
    instructions.md       # extraction scope and abstention rules
    input.schema.json     # bounded source content + evidence request
    output.schema.json    # candidates + source references
    tool_policy.yaml      # permitted reads; no write capability
    validators.py         # shape, provenance, dates, units
    eval_cases.jsonl      # normal, ambiguous, adversarial examples

registry:
  serum_creatinine: structured_lab_adapter_then_extract_lab_observation
  culture_result: structured_microbiology_adapter_then_extract_culture
  allergy_class: structured_allergy_adapter_then_reconcile_terminology

Use structured source fields directly when they satisfy the contract. Do not call an agent to copy a database value. Bound model calls by document size, tool count, runtime, and retry budget; exhaustion produces an explicit unresolved status. Spokes return to the hub instead of delegating freely to each other.

04 / THE REUSABILITY SEAM

A snapshot is evidence, not a chat history

A snapshot binds immutable evidence to a patient and encounter. Store all relevant candidates and the accepted value separately. Every accepted fact has provenance, an observation time or explicit unknown, and the method used to accept it. A model-generated confidence score is diagnostic metadata, not authority to proceed.

Field groupRequired meaning
Identity and versionSnapshot ID/version, opaque patient and encounter references, creation time, schema version, normalization-policy version.
Clinical valueEvidence key, typed normalized value, canonical unit, original value/unit, evidence status, candidate IDs.
Clinical timeobserved_at is the measurement/specimen time appropriate to that concept. Keep report time and ingestion time separately. Never substitute ingestion time for freshness.

Freshness and reconciliation rules

  • Evaluate freshness against a recorded UTC decision time: 0 ≤ evaluated_at − observed_at ≤ max_age. Missing or impossible timestamps block freshness-dependent decisions.
  • Represent missing, pending, negative, and not performed as distinct states. A pending culture is not a negative culture; no allergy record is not evidence of no allergy.
  • Match specimen, encounter, observation type, and reporting status before comparing results. Preliminary and amended results need source-specific policies reviewed by the clinician.
  • Normalize units only through tested conversion rules. Unsupported units or terminology remain unresolved; do not ask the model to guess a conversion.
  • Do not define a universal “P beats C” rule or average conflicting values. Clinically meaningful conflicts pause for review unless an approved concept-specific precedence rule resolves them.
  • Treat source documents as untrusted data. Instructions inside a document cannot change tool permissions, extraction policy, or tree behavior.
05 / TREE AS DATA

The executor owns every transition

Publish trees as immutable artifacts after schema checks, graph validation, regression tests, and clinical approval. Pin the artifact hash and version at run creation. The executor resolves evidence keys from the snapshot and applies an allowlisted operator with explicit types. Never use eval, executable YAML tags, or model-generated code.

schema_version: "1.0"
tree_id: tree_a_demo
version: "0.1.0"
entry_node: culture_gate
nodes:
  culture_gate:
    type: decision
    requires:
      - key: culture_result
        value_type: enum
        allowed_values: [positive, negative, pending, not_performed]
        max_age_hours: 24       # Synthetic example, not a clinical policy
        usable_values: [positive, negative]
    predicate:
      op: equals
      evidence: culture_result
      value: positive
    on_true: positive_path
    on_false: negative_path
    on_unavailable: review_evidence
  review_evidence:
    type: review
    reason: evidence_unavailable
    resume_at: culture_gate
  positive_path:
    type: terminal
    output_code: DEMO_POSITIVE_PATH
    mandatory_review: true
  negative_path:
    type: terminal
    output_code: DEMO_NEGATIVE_PATH
    mandatory_review: true

The 24-hour limit and output codes demonstrate structure only. Tree authors must obtain clinical approval for actual freshness limits, thresholds, and recommendations. Pending evidence follows on_unavailable before predicate evaluation.

How traversal works in plain Python

The controller asks for evidence; the executor chooses the branch. In the example above, a usable positive culture selects positive_path, a usable negative culture selects negative_path, and pending or missing evidence selects the review route before comparison.

# Illustrative application pseudocode, not an ADK SDK API.
# Called for a decision node; review/terminal nodes have separate handlers.
def evaluate_decision(node, snapshot, evaluated_at):
    issues = validate_requirements(
        node.requires, snapshot, evaluated_at
    )
    if issues:
        return ReviewRequired(node.on_unavailable, issues)

    # Registered, typed operators only. No eval() and no LLM call.
    predicate = node.predicate
    value = snapshot.accepted_value(predicate.evidence)
    result = OPERATORS[predicate.op](value, predicate.value)
    next_node = node.on_true if result else node.on_false
    return Transition(next_node, result, evidence_refs(snapshot, node))

# The controller supplies the immutable snapshot, then atomically
# persists this result with the run checkpoint and audit event.

Execution contract

  1. Load the pinned tree and current checkpoint; acquire a fenced per-run lease.
  2. Validate required evidence, type, units, usability, and freshness. Missing, stale, conflicting, or invalid evidence triggers its recorded review reason.
  3. Evaluate the predicate only with accepted, usable evidence. Return a typed result and next node; no LLM participates.
  4. Commit the transition, evidence references, predicate result, and audit event atomically with the new run revision.
  5. Stop at review or terminal state, or schedule the next bounded execution step. Mandatory-review output remains provisional until approved.

Reject unreachable nodes, unknown operators, missing transition targets, ambiguous branch definitions, and cycles in the decision graph. Review resumption is a lifecycle operation, not an unrestricted graph loop. Use an execution step limit as a final guard. Initial operators: typed comparison, membership, and Boolean composition; add operators only with tests and versioned semantics.

06 / HUMAN REVIEW & DURABILITY

Pause the run. Release the process.

A clinician may act hours later, after the original Cloud Run instance has disappeared. Persist the run, review request, and pending work before returning. An ADK long-running tool can represent the human wait, but the application state machine remains authoritative. ADK resume behavior and custom-agent support must be tested against the pinned SDK version. [2]

What is persisted

The run stores its revision, status, current node, pinned tree/policy versions, snapshot reference, last event sequence, pending tool operation IDs, ADK session/invocation references, and lease fencing token. Review tasks include reason codes, evidence/path digest, allowed actions, reviewer role, and expiration policy.

Review semantics

  • Evidence review: a clinician supplies or selects a sourced value with rationale. Create a new snapshot and reevaluate affected nodes. “Approve” cannot make a missing required fact true.
  • Recommendation review: approve or reject the exact proposed output and evidence/path version. A stale review submission returns a conflict and requires refresh.
  • Changed evidence: recompute from the earliest affected node; invalidate downstream decisions and approvals in the active path. Preserve prior versions as superseded audit history.
  • Expired evidence: obtain new evidence or request renewed review according to the tree. Rechecking freshness uses a new recorded decision time; historical replay uses the original time.
  • Cancellation and rejection: terminate explicitly without a reviewed recommendation. Timeouts never imply approval.

Recovery and dual-store consistency

Commit checkpoint, audit event, and outbox work record in one Firestore transaction. A dispatcher delivers the outbox item to Cloud Tasks; deterministic task IDs and consumer idempotency absorb repeated enqueue attempts. A scheduled sweeper finds unsent work and expired leases. Cloud Tasks delivery can be repeated, so delivery is not an exactly-once guarantee. [3]

Cloud SQL session history and Firestore are not one transaction. Store a durable operation ID before invoking ADK. Accept its validated result into Firestore only once; if a crash leaves completion uncertain, retry or recover that operation without repeating a committed clinical transition. ADK state cannot overwrite the clinical checkpoint. Use bounded retries with backoff; exhausted work becomes a visible failed/review-required state.

08 / MEASURE & IMPROVE

Arize AX supports the iteration loop

Instrument ADK calls and custom executor/review spans using OpenTelemetry/OpenInference, with AX as the destination. Apply an allowlist and redaction before export, including exception bodies and automatic prompt capture. Keep real patient identifiers, raw documents, and source row IDs inside GCP; export synthetic or approved de-identified examples with opaque correlation IDs. AX experiments compare application versions against curated datasets. [6] [7]

The change loop

  1. Capture a failure or clinician correction; classify the cause as source, extraction, policy, tree, workflow, or explanation.
  2. Turn it into a reviewed test case. Keep a held-out patient-separated test set so prompt tuning does not contaminate evaluation.
  3. Change one versioned component and run AX experiments plus deterministic regression tests across all onboarded trees.
  4. Compare safety-critical slices and false acceptance, not only average accuracy. The clinical expert approves clinical thresholds before pilot release.
  5. Promote the exact tested bundle; shadow it first. Monitor regressions and retain the previous bundle for new-run rollback.

Audit event minimum: run/event ID, node ID, tree and snapshot version, evidence candidate references and source locations, observed/evaluated times, predicate/result/next node, model and skill versions when used, review identity/action/rationale, and correlation IDs. Store decision evidence and outcomes, not hidden model reasoning. Clinician corrections become eval candidates only after curation and de-identification.

AX export failures should queue telemetry for retry without blocking clinical execution when the local audit was committed. A failure to persist the authoritative clinical audit must stop advancement. Alert on stuck runs, exhausted retries, audit write failures, and increased evidence rejection rates.

09 / FOUR-ENGINEER DELIVERY

Parallel work, shared integration milestones

Use a temporary two-and-two split, with daily integration against shared fixtures. Do not let one half spend weeks producing data mappings while the other builds a generic platform in isolation. Both tracks should demonstrate the same Tree A case from the first milestone.

Choose the first tree deliberately

Choose an available-data tree with clear clinical ownership, a manageable number of paths, and at least one realistic freshness or review requirement. Tree B should stress a different capability, such as document extraction or conflicting sources. If Tree A access is blocked, use the next ready tree as the first implementation rather than waiting for every source.

The discovery matrix should list each tree’s evidence keys, source/field, access owner/status, patient join, units and codes, observation-time semantics, freshness policy, conflict policy, known data gaps, and example cases. That matrix is the shared backlog, not a separate discovery report.

Keep the feedback cycle short

Use small daily changes, one integration demonstration each day, and twice-weekly clinical case reviews. Run synthetic fixtures in CI before source access is available. Share ownership through code review across the data/platform boundary. Estimate calendar duration after Stage 1 reveals access delays and clinical complexity; do not treat these stages as fixed one-week sprints.

11 / VERIFICATION & ROLLOUT

Release by evidence, not by tree count

ScenarioExpected result
Predicate boundariesBelow/equal/above threshold, enum values, and Boolean combinations follow approved paths exactly.
Missing or unusable evidenceNull, pending, not performed, invalid unit, unknown timestamp, and stale values never fall through as a clinical negative.
Freshness boundaryExactly at the limit is accepted under the defined inclusive rule; beyond it or future-dated evidence is blocked.
Conflicts and correctionsConflicts trigger review; amended evidence creates a new snapshot and invalidates dependent approvals.
Extraction adversariesWrong-patient documents, embedded instructions, fabricated citations, and malformed model outputs fail validation or remain unresolved.
Workflow fault injectionCrash before/after checkpoint, repeated task delivery, duplicate clinician action, and concurrent workers do not duplicate committed transitions.
Pause over timeRestart on another instance resumes safely; aged evidence is rechecked and outdated approvals are rejected.
Audit and replayEvery committed path step has provenance; replay with original versions and evaluation times reproduces the path.
Cross-tree changeA skill, model, schema, or executor change runs regression tests on A/B/C and detects unintended path changes.
Access and telemetryUnauthorized patient/run access is denied; exported spans and errors contain no prohibited patient content.

Technical release gates require all approved deterministic path and safety tests to pass. Clinical acceptance additionally requires representative clinician-labeled evaluation, documented thresholds, and signed-off tree semantics. A small passing dataset is not evidence of general clinical validity.

Roll out through synthetic cases → representative de-identified cases → authorized shadow runs → supervised pilot. Keep all initial recommendations behind clinician review, including antibiotics. New deployments affect new runs; in-flight runs retain their tree, policy, and skill bundle unless explicitly cancelled and restarted. Rollback changes the default bundle for new runs and preserves audit history.

Reuse is demonstrated when: Trees B and C run through the same executor and review lifecycle, differences are expressed through approved data/skills, and changes to shared components are evaluated across all trees.
