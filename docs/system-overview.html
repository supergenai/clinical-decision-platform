Tree A · Clinical Decision Support · System Overview

Deterministic pipeline, one bounded AI step

A clinical decision tree evaluates known evidence with fixed, testable logic. An LLM (via Google ADK) is used for exactly one job — turning documents, images and free text into cited candidate values. It never decides anything clinical.

1 · Architecture: what's deterministic, what isn't

Deterministic Python — same input, same output, always Non-deterministic — LLM inference, bounded and validated

2 · Who does what: LLM (ADK) vs. deterministic code

Handled by the LLM ADK

  • Routing a missing evidence key to the right tool (structured → BigQuery adapter; unstructured → RLM/LightRAG)
  • OCR and field extraction from scanned lab reports and images
  • Extracting a typed value from free text, with a citation to the source span or region
  • Abstaining when a value isn't clearly present

Handled by deterministic Python no LLM

  • Which evidence a tree node requires, and when to fetch it
  • Querying BigQuery (P, C) with parameterized, scoped reads
  • Validating every candidate: type, unit, freshness, provenance, identity match
  • Evaluating tree predicates and choosing the next node
  • Review state, approval, audit chain, kill switch
  • Explanations (fixed templates bound to recorded evidence and path)
QuestionWho answers it
Is this value present in the document?LLM (ADK/RLM) — extraction, with abstain option
Is this value usable (fresh, correct unit, right patient)?Deterministic validator — same rule for every source
Which branch does this evidence lead to?Deterministic executor — pure function, replayable
Is the recommendation approved?Human clinician — always, no exceptions

3 · Outcome measurement

Two different things are measured, on purpose: whether the deterministic core is correct (it either is or isn't — tested, not measured on a curve), and whether the LLM extraction step is good enough (measured continuously, with a hard floor on the failure that matters).

Deterministic layer — pass/fail, not a score

  • Path correctness: every clinician-approved Tree A path passes in CI, exactly, every time
  • Replay equality: re-running a completed case against its stored snapshot reproduces the identical path
  • Fail-closed rate: 0 recommendations issued on missing, pending, stale or conflicting evidence
  • Audit integrity: hash chain unbroken; no gaps between events
  • Kill switch: suspended bundle halts in-flight runs within 5 minutes

LLM extraction layer — measured continuously (Arize AX)

  • False acceptance — hard gate at zero: a wrong value accepted as fact never happens on the safety suite
  • Citation validity: 100% of accepted candidates cite a real, verifiable location in the source
  • Field accuracy: against a clinician-labeled, patient-disjoint held-out set — reported per evidence type (structured field, free text, OCR'd image), not as one blended number
  • Abstention correctness: the model says "not found" when it should, instead of guessing
  • Cost and latency per run: tokens, tool calls, p95 time — tracked so orchestration overhead doesn't silently grow

Why the two are never blended into one number

A 95% blended accuracy figure can hide the one case that matters — a wrong lab value silently accepted as real. So the release gate is deliberately asymmetric: the deterministic core must be 100% correct on every approved path (it's code, not a model — there's no reason to accept less), and the LLM layer is judged on a zero-tolerance floor for false acceptance plus a separate, honestly-reported accuracy trend. Passing on average is not a pass.
