What “done” means on day 70

A clinician can open a Tree A case in staging and see which evidence was found and where it came from. They can follow the exact path the tree took, then approve or reject. Every step is audited and replayable from stored data, and missing, pending or stale evidence never becomes a recommendation. The extraction agent has passed thresholds agreed in advance, on a held-out set it was never tuned against. No patient data exists anywhere in the MVP: not in Devin, not in Arize, not in staging.

Decisions needed this week

  1. Architecture ADRs: a single Postgres store, a Postgres job queue in place of Cloud Tasks, and direct BigQuery reads through authorized views, with no mirror copy.
  2. The day-70 outcome is “shadow-ready” on synthetic data. Real data can move earlier only through the Day 30 stretch below.
  3. Regulatory owner: who receives the intended-use statement on day 7.
  4. Devin is SaaS: confirm that Devin only ever touches the dev project and synthetic data.

Assumptions behind the dates

  • 70 calendar days: 60 days of build with code freeze at the end of day 60, then 10 days of testing.
  • Devin seats, Arize AX, GitHub and a GCP dev project are ready on day 1.
  • Clinical lead at about 0.5 FTE, with calendar holds booked on day 1.
  • The data team provides P and C schemas and metadata access by day 10.
  • Planning velocity is 5 pts/engineer/week in weeks 1–2, then 6.5 once Devin is productive. This ~1.3× lift is an assumption and gets measured at Day 30.

MVP scope

Scope is driven by one rule: nothing that protects a patient gets cut for the date. What gets cut is what only matters once real data flows.

In the 70-day MVP

  • Tree A only, with clinician-signed expected paths
  • P and C adapters on BigQuery (dev dataset with real schemas, synthetic rows)
  • Terminology registry, identity binding, timezone rules
  • Eager snapshot, deterministic validator, conflict detection, revalidation before approval
  • Tree compiler, typed operators, pure executor, immutable bundles, kill switch
  • Postgres run store, state machine, job queue, hash-chained audit
  • One ADK extraction skill with Arize AX evals, adversarial set, frozen held-out set
  • Review API and screen (approve, reject, cancel), explanation templates, approval gating
  • Sign-in and roles in staging, fail-closed state, PHI-leak test
  • Devin environment, CI lanes, guardrails for AI-written code, staging deploy lane
  • Test window: verification, fault injection, clinician UAT, held-out eval, restore test

Phase 2: after access and Day-70 go

  • Authorized views on real P and C; real-data integration; prod data validation
  • Prod project, JIT access, attested deploys
  • PHI access log, real care-relationship source, break-glass, pen test
  • WORM audit export, replay tool, drift monitors, operational alerts
  • Evidence resolution UI, review expiry, automation-bias telemetry
  • Dual-annotated real-data eval set, model retirement registry
  • Shadow protocol, shadow mode, go/no-go for supervised pilot
  • Tree B and the cross-tree regression gate
  • Reconciliation and LLM explanation agents (still deferred)

Day-70 exit criteria

  1. Every approved Tree A path and safety case passes in CI and in staging. Missing, pending and stale evidence never produce a recommendation.
  2. On the frozen held-out set, the extraction skill has zero false acceptances, 100% citation validity, and field accuracy at or above the pre-registered target (CDP-107).
  3. Fault injection shows zero duplicated committed transitions across 500 randomized runs, and the kill switch halts in-flight runs within 5 minutes.
  4. At least three clinicians complete UAT on 25 scripted cases with no open critical issues.
  5. Every MVP hazard has a verified control, and residual risks are listed for Phase 2.
  6. The PHI-leak test is green, and no environment, Devin session or Arize space holds real patient data.
  7. Phase 2 is re-estimated from actual access status.

Integration rules: every interface is read-only toward clinical systems. Every call has a timeout and a budget, and any failure becomes an explicit state that fails closed. Patient scope comes from the run, never from tool arguments. Views and APIs are versioned (cdp_evidence_v1, /v1), and each interface has a contract test in the integration lane. Timeouts are starting values, to be tuned from week-4 latency measurements.

How the agent gets built and improved

The loop is the product. Teams new to agents usually tune prompts by eye. This loop makes every change an experiment that CI measures and a human approves.

  1. Story with acceptance testsA human writes the failing tests and names the eval cases. Devin never writes its own oracle.
  2. Devin session in devSynthetic data only. Knowledge and Playbooks carry the architecture rules.
  3. Fast and integration lanesTypes, unit and property tests, tree compiler, import rules, then end to end in docker compose.
  4. Agent-eval laneAX experiment on the golden and adversarial sets against the main baseline, with deltas posted to the PR.
  5. Human reviewCODEOWNERS: the clinical lead on trees and golden sets, two humans on executor, validator and authz.
  6. Merge and nightlyFull golden set on the live model, repeated three times to show variance, plus fault injection and a cost report.
  7. Release laneHuman-triggered deploy to staging, with bundle hashes recorded. The held-out set is used only at the Day-70 gate.
  8. Friday demoThe same five synthetic cases every week, plus the scorecard.
  9. Failure → regression caseTag the trace, classify the failure, add the case by PR with clinical approval, then back to step 1.

Enablement for a first-time agentic team

  • Days 2–3 bootcamp: ADK and the hub/skill boundary; eval-driven development in AX (write the evaluator before the prompt); the Devin workflow and guardrails; clinical safety basics (missing is not negative, hazard log).
  • Pairing: the lead pairs with each engineer on their first Devin-driven story and their first skill experiment.
  • Thursday agent clinic (30 min): one real failure trace, one eval lesson, one Devin lesson.
  • Reading list: ADK docs for the pinned version, AX datasets and experiments, the HLD, and this plan.

Tooling and budget

  • Devin seats for all 5, with Knowledge and Playbooks set up in week 1
  • Arize AX with spaces cdp-dev, cdp-staging, cdp-holdout and role-scoped keys
  • GCP dev and staging projects with Vertex AI quota, plus a monthly model-spend cap for eval lanes, tracked on the scorecard
  • GitHub: Actions minutes, merge queue, CODEOWNERS, branch protection
  • Jira: import the CSV, one-week sprints, “accepted in demo” as the final status

Product owner checkpoints

Day 30

Is the skeleton real, and is Devin actually helping?

Show

  • POST a Tree A run in dev and get a recorded path and audit trail
  • All Tree A paths passing on fixtures, signed by the clinical lead
  • P adapter on the BigQuery dev dataset; C adapter in progress
  • AX baseline scorecard from the spike skill on golden set v1
  • All CI lanes and guardrails enforced
  • Hazard log v1; intended use with counsel; freshness gate numbers

Decide

  • Continue if accepted points are ≥ 85% of plan
  • Re-scope with the cut list if below 85%, or if the Devin lift is under 1.1×
  • Pull the stretch forward: if real BigQuery access is approved and counsel is engaged, move CDP-1204 and the PHI access log into I6–I7
  • Change Tree A if p95 load lag exceeds its freshness limits

Feature-complete in staging?

Show

  • All 25 UAT cases runnable in staging through the review screen
  • Extraction scorecard against pre-registered thresholds
  • Fault-injection suite green
  • Test plan, UAT schedule and clinicians confirmed

  • Enter the test window as planned
  • Or use up to 3 test days for fixes and shrink UAT scope. Don't extend the build.
Day 70

Shadow-ready?

Show

  • Exit criteria scored, with evidence links
  • UAT findings and held-out eval report
  • Residual risks and Phase 2 re-estimate from access status

Decide

  • Start Phase 2 (real data, shadow mode)
  • Fix and retest with named gaps and dates
  • Stop or re-think if the extraction skill can't meet thresholds

Cut list, in order, if Day 30 shows a shortfall: screen iteration (CDP-808); conflict detection falls back to “any second candidate goes to review” (CDP-404); document retrieval uses synthetic files in Cloud Storage (CDP-307); the C adapter reduced to the culture concept only (CDP-305). Last resort: take extraction out of Tree A's clinical path and keep improving the skill behind the eval gate. Never cut: kill switch, audit chain, fail-closed state, approval gating, the PHI-leak test, or protected oracles.
